# Who owns child order

The order children sit in is a single piece of state, and both you and the user
have a claim on it: you know which panes should exist, they decide how the panes
are arranged. Deciding who writes that state is the choice this chapter is
about, and getting it wrong is why a drop can appear to succeed and then undo
itself on the next render.

`container.childOrder` is the single canonical ordering. Layout, `useChildren`,
snapshot and DnD all read it, and every mutation that adds, removes, moves or
reorders rewrites it.

The question is who writes it.

## The store owns it

Default for the imperative path. `moveNode`, `reorderInParent` and
`setChildOrder` write it, and a drop or a keyboard move commits.

## JSX owns it

Default for `<Zone>`. Sibling order is reconciled into `childOrder` on every
render, so a drop that reorders is reverted on the next one.

## The host owns existence, the user owns arrangement

The common real case: your app knows *which* panes exist, the user decides how
they sit. Pass `preserveStoreOrder`:

```tsx
import { preserveStoreOrder } from 'windease/react';

<Zone sort={preserveStoreOrder}>
  {panes.map((p) => <Panel key={p.id} id={p.id} />)}
</Zone>
```

Reconcile short-circuits: no `setChildOrder` runs, so a drop survives the next
render and no `arrange` lock is needed. Children the binding did not observe
keep their store positions.

`defaultChildSort` is the other built-in — numeric `order` ascending, then
declared position. A custom `ChildSort` receives the observed children and the
full current id list and returns the final order.

## Taking back just this decision

`<Container onChildOrderChange>` makes order controlled: a drop hands you the
list it *would* have written and the store is left alone. See
[7.8](/?story=guide--07-customization--7-08-controlled-placement-and-order).
