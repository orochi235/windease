# Wiring a drag

DnD is opt-in and needs one more provider than layout does.

**React**

```tsx
<DragProvider>
  <Container parentId={zoneId} chrome={chrome} />
</DragProvider>
```

Wrap the grabbable part in `<DragHandle>`, and register each container as a drop
target:

```tsx
<DragHandle nodeId={node.id}>
  <header className="pane__title">{title}</header>
</DragHandle>

useDropTarget(zoneId, ref);
```

The presets take `acceptsDrops` instead, and `<Panel draggable>` wraps its whole
content in a handle.

**Core**

A host not driving DOM elements — a canvas surface, a test — drives `DragEngine`.
Same ownership, acceptance and hit-test logic; geometry as data, no listeners:

```ts
const engine = new DragEngine(store);
engine.addDropTarget(zoneId, { bounds: () => ({ x: 0, y: 0, w: 400, h: 300 }) });
engine.tryBegin(panelId);
engine.updateHoverByPoint(x, y);
engine.drop();
```

`DragController` is that engine plus the DOM: element rects, `parentElement`
depth for innermost-wins, `data-drop-target` / `data-drop-rejected` attributes,
window-level Escape and pointerup safety nets, and per-frame coalescing.

## Who gets to refuse

Six answers, in order:

- `lock.move` on the source — per-node drag suppression
- `lock.dragOut` on the source's parent — zone-level
- `lock.accept` on the target — zone-level refusal
- the destination strategy's `canAccept(items, options)`
- `acceptPolicy` on the container, which overrides that answer
- a deprecated `canAccept(sourceId)` on the drop target, removed at 2.0.0

A `lock.accept` refuses regardless of any policy. See
[8.5](/?story=guide--08-customization--8-05-accept-policy).
