# Locks

`node.lock` answers **who may operate on this node?** It is enforced by the
store, which throws `LockedError` — not a UI hint.

```ts
store.setLock(id, { destroy: true, move: true });
store.setLock(id, true);   // every axis this node supports
```

| Axis | Refuses | Needs |
| --- | --- | --- |
| `move` | being moved | `membership` |
| `resize` | `size` / `span` changes | `membership` |
| `destroy` | being destroyed | always |
| `accept` | taking a drop | `container` |
| `dragOut` | children leaving | `container` |
| `arrange` | children being rearranged | always |

Which axes apply follows from capabilities. **Unsupported axes are dropped
silently rather than rejected**, so a host can pass `true` without branching on
node shape.

`lock` is node-intrinsic like `meta` — it survives `moveNode`.

## `arrange` is broader than it looks

It governs whether a container's children may be rearranged *including whether it
may acquire any*, which is why it is checked on `ensureContainer` too and not
gated on a container already existing.

## `destroy` is checked over the whole subtree

`destroyBlockedBy(store, id)` returns the first node in the subtree — `id`
included — carrying `lock.destroy`, or null. It returns the *blocker* rather than
a boolean so a refusal can name which descendant refused.

## A lock is not a policy

A policy is consulted and may defer. A lock refuses regardless of what any
policy answered — `acceptPolicy` returning `true` does not get past
`lock.accept`. See [7.4](/?story=guide--07-customization--7-04-the-policy-contract).

`acceptsDrops` is a third thing again: a React prop that registers an element as
a drop target at all. Not locking a zone is not the same as opting it in.
