# The capabilities in full

A capability is an optional field on the node record, and its **presence is the
grant**. A node that has a `container` field can host children; a node without
one cannot, and there is no separate flag, type tag or subclass saying so. The
field is both the permission and the storage — `container` holds the child
order and the strategy that arranges them, `membership` holds the parent id and
this node's placement within it.

That is why the question "what kind of node is this?" has no direct answer in
this library. There is no discriminant to switch on, because the shape *is* the
answer: you ask whether a node has children by asking whether it has a
`container`. `node.kind` looks like it should serve that purpose and does not —
the core stores it, never reads it, and will happily give you a node whose
`kind` is `'panel'` and whose fields say otherwise. Checks are structural all
the way down, which is also why the errors are: an operation that needs a
capability a node lacks throws `CapabilityMissingError` rather than failing
somewhere further in.

The payoff is that combinations cost nothing. Three optional fields give eight
possible shapes, and the useful ones already have names — a zone is
`container` with no `membership`, a panel the reverse, a group is both. None of
those is a type in the codebase; they are conventional names for combinations,
and `<Zone>` and `<Panel>` are `createNode` calls that pick one. A tray inside a
window needs no new component because it is a node that happens to carry both
fields, and recursion falls out of the same fact.

## The four

- **`lifecycle`** — the only one every node carries, so it is less a capability
  than the baseline. A state machine running
  `mounted → visible ↔ hidden → destroyed`, which is why a registered node is
  invisible until `showNode`. Covered in
  [2.1](/?story=guide--02-state-machines--2-01-lifecycle).

- **`container`** — *can I have children?* Holds `childOrder` (the canonical
  ordering), the `strategyId` and `config` that arrange them, and the flags a
  container answers for: `allowsPinning`, `autoUnsplit`, `lastFocusedId`. A node
  with this field is a container regardless of what it is called.

- **`membership`** — *do I have a parent?* Holds `parentId`, this node's
  `placement` within that parent, and the transit machine that makes a move
  between parents atomic. **The opposite question from `container`**, and the
  two are independent: having children says nothing about having a parent.

- **`focus`** — can this node take focus? The only one that is opt-in per node
  rather than implied by the tree's shape: `createNode({ focus: true })`.
  `<Panel>` passes it and `<Zone>` does not, so a container is not focusable by
  default and making one so is a deliberate act.

## What each one holds

```ts
interface ContainerCap {
  strategyId: string;
  config: unknown;
  childOrder: NodeId[];
  allowsPinning: boolean;
  autoUnsplit?: boolean;
  lastFocusedId?: NodeId;
  state?: unknown;
}

interface MembershipCap {
  parentId: NodeId;
  placement: Record<string, unknown>;
  transit: TransitCap;
}
```

Two fields inside these are easy to misuse.

**`childOrder` is the single canonical ordering.** Layout, `useChildren`,
snapshot and drag-and-drop all read it. Prefer `setChildOrder`,
`reorderInParent` and `moveNode` over writing to it, so the invariants and the
events come with the change.

**`lastFocusedId` is session state.** The store maintains it — written on
`focusNode`, cleared when that node is removed or reparented — and it is
deliberately **not serialized**, so a reload does not restore a focus memory
that no longer matches what the user did.

## Fixed at construction

Which capabilities a node has is decided in `createNode` and does not change.
So a node that cannot take a child cannot be taught to; the fix for a
`CapabilityMissingError` is at the construction site, not the call that failed.

`ensureContainer(id, strategyId, config)` is the single exception, promoting a
node to a container after the fact. It is gated by `lock.arrange` — which is
why that axis is checked even on nodes that have no container yet, since
acquiring one is exactly what it has to be able to stop.

Beyond that the core validates structure and nothing else: `parentId` must name
a node that has a `container`, no node may become its own ancestor, and at most
one node holds focus. It never relates `kind` to any of it.
