# Focus

Focus is which single pane the user is currently *in* — the one their keys go
to, and the one a screen reader is describing. windease tracks that itself
rather than reading it off the document, because a pane is a node in a tree
long before it is an element, and a canvas host has no `activeElement` to read.

The machine on each node records only whether that node holds it. The rule that
there is exactly one such node lives in the store, above them all.

`focus` is also the one capability that is opt-in per node rather than implied
by shape.

```ts
createNode({ id, parentId, focus: true });   // focusable
createNode({ id, parentId });                // not
```

`<Panel>` passes `focus: true`. `<Zone>` does not — a container is not a focus
target by default, and making one focusable is a deliberate act.

## One focused node, enforced by the store

The machine is `focused ↔ blurred`, but the invariant lives above it: the store
allows exactly one focused node and blurs the previous one for you.
`store.focusedId` is the answer; `canFocus(id)` asks whether a node could take
it.

`hasFocus(id)` is deprecated and reads as "does this node have a focus machine",
which is almost never the question. Compare `store.focusedId` instead.

## Focus survives what removes its holder

Destroy or hide the focused pane and the store picks a successor rather than
dropping focus to the document — next visible sibling, then previous, then the
parent's remembered child, then the parent, then the first visible leaf. It
reports the choice on `focus.successor` with a `reason`.

That rule is replaceable; see
[7.6](/?story=guide--07-customization--7-06-choose-successor).
