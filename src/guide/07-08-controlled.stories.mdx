# Controlled placement and order

The same idea as a policy — the host taking back a decision — but for values
rather than rules.

## Why you need this

A seam drag writes `placement.size` to the store. If you *declare* `placement` on
a preset instead, **you** own it: the prop is reconciled on every render, so the
drag is reverted on the next one. Declare one or the other, not both.

`onPlacementChange` says so, and the gesture hands you the bag it would have
written, leaving the store alone.

**React**

```tsx
const [h, setH] = useState(200);

<Panel id={a} placement={{ size: { h } }} onPlacementChange={(next) => setH(next.size.h)} />
<Panel id={b} />   {/* uncontrolled — its own drags commit as usual */}
```

Controlled and uncontrolled panes mix freely in one row.

**Core**

```ts
host.registerPlacementControl(id, (next, change) => {
  // change: { affordanceId, parentId }
});
```

Registering one is what makes the child controlled. Absent context is a no-op
rather than an error, so the same component renders inside a laid-out parent and
standalone.

## Order, the same way

```tsx
<Container parentId={zoneId} onChildOrderChange={(ids, change) => setOrder(ids)} />
```

A drop hands you the list it would have written. Only **library-mediated**
gestures are intercepted: `store.reorderInParent` called directly still commits,
since that is the host acting on itself.

## Do not copy the bag

The placement you receive is the whole next bag, not a patch. Storing a reference
to it and mutating it later is a bug — treat it as the value to render from.

`preserveStoreOrder` is the opposite trade: the store keeps order and JSX stops
fighting it
([3.5](/?story=guide--03-building-the-tree--3-05-who-owns-child-order)). Reach for
controlled order only when the host genuinely owns arrangement.
